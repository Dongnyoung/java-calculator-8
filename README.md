# java-calculator-precourse

## 문자열 덧셈 계산기

> 입력된 문자열을 구분자 기준으로 분리하고, 숫자들의 합을 계산하는 프로그램이다.

> MVC 구조와 다양한 디자인 패턴(전략, 컴포지트)을 적용하여 유지보수성과 확장성을 높였다.

## 구현할 기능목록

**클래스 단위로 기능을 정의**

### `CalculatorController`
- 애플리케이션의 흐름을 제어하는 컨트롤러
- 입력 → 유효성검사 → 파서선택 → 파싱 → 연산 → 출력의 순서로 실행 흐름을 관리

### `Input`
- 사용자로부터 문자열을 입력받음

###  `InputValidator`
- 입력 문자열의 유효성을 검사
  - 빈 문자열 검증
  - 커스텀 구분자("//구분자\n") 규칙 검증
  - 잘못된 위치, 허용되지 않은 구분자 검증

### `Parser` 인터페이스
- 문자열을 숫자 토큰으로 파싱
- **전략 패턴(Strategy Pattern)** 적용으로 다양한 파싱 규칙을 확장 가능
  - `CommaColonParser`: 쉼표(`,`), 콜론(`:`) 기준으로 파싱
  - `CustomParser`: `//`와 `\n` 규칙을 따르는 커스텀 구분자 파싱

### `TokenValidator` 인터페이스
- 파싱된 토큰들의 유효성을 검사
- **컴포지트 패턴(Composite Pattern)** 적용
  - Leaf:`NullValidator`: 빈 토큰 검증
  - Leaf: `NumberTokenValidator`: 숫자 형식 검증
  - Composite:`CompositeValidator`: Leaf 검증기들을 순회하며 유효성검사 

### `Operator` 인터페이스
- 파싱된 숫자들의 합을 계산 (`AddOperator클래스`)
- 향후 사칙연산 확장을 위해 `Operator` 인터페이스로 추상화

### `Output`
- 계산 결과를 출력

## 1. 설계 과정 (Thinking)

### 1. 고민의 시작
처음에는 단순히 입력을 받고 구분자에 따라 덧셈만 수행하면 되는 문제라 생각했지만,  
유효성 검사, 파싱 규칙, 예외 처리 등 세부적인 책임이 많아 구조적 접근이 필요하다고 느꼈다.

MVC로 접근하려 했지만 `Controller`에 로직이 집중되는 문제를 발견했고,  
이를 해결하기 위해 **전략(Strategy)** 과 **컴포지트(Composite)** 패턴을 적용하였다.

### 2. 전체 흐름
```
Application →Input (입력) →InputValidator (입력 검증)

→ ParserResolver (파서 선택) → Parser (파싱) → TokenValidator (토큰 검증)

→ AddOperator (연산) → Output (출력)
```
---

### 3. 리팩토링 과정

#### 1) 초기에는 `if-else`문으로 유효성검사를 처리 → **하나의 클래스로 분리(InputValidator)**

#### 2) `CalculatorController`가 모든 로직을 담당 → **객체 주입(의존성 분리)** 으로 책임 분리

- 토큰 검증 로직이 중복 → **컴포지트 패턴**으로 통합 및 확장성 확보
- 파서 로직 중복 → **전략 패턴**으로 해당 파서를 선택할 수 있도록 resolver를 두었음.
- add연산 클래스화 → 인터페이스로 두어 향후 사칙연산에 대한 OCP원칙을 따름.

`InputValidator`와 `TokenValidator`를 분리한 이유
- 입력 문자열 검증과 토큰 검증은 성격이 완전히 다르기 때문이다.
- 하나는 입력 형식의 적합성, 다른 하나는 파싱 이후 데이터의 유효성을 책임진다.
- 따라서 같은 검증기라고 하더라도 성격이 달라서 input,token패키지로 나누었다.


## 3. 적용 패턴

### MVC
전체적인 흐름은 MVC흐름이다.
사용자 요청이 들어오면 Controller를 통해 로직을 수행하고 model,view를 리턴하며 model을 이용하여 view를 랜더링한다.
해당 프로젝트에서도 Controller를 통해 로직을 수행하고 도메인들을 이용하여 Output을 내보낸다.

#### model로 하지 않고 domain이라고 한 이유

- 단순히 데이터를 담는 객체(POJO, DTO) 모음이 아니다.
- 프로그램의 핵심 비즈니스 로직이 구현된 영역이기 때문이다.
- domain에는 operation, parser, validation과 같은 실제 계산기 로직의 중심 기능들이 포함되어 있다. 
- 이들은 단순한 데이터 구조가 아니라, 각각 규칙을 수행하고, 계산을 처리하며, 입력을 해석하는 주체적인 역할을 가진다.
- model은 “데이터의 형태”를 표현하는 수준에 그치는 반면, domain은 “도메인(비즈니스) 문제를 해결하는 규칙과 행위”를 포함한다.
- 따라서 이 프로젝트에서는 domain이라는 이름이 훨씬 더 본질에 맞으며, 프로그램의 의도를 잘 드러낸다고 생각하여 domain이라 두었다.


### Parser interface
전략패턴(Strategy Pattern)을 사용한 이유?
- 초기에 CalculatorController내부의 parse메소드에서 if-else문으로 많은 부담을 갖게 되었다.
- 이를 해결하기 위해, “파싱 방법(알고리즘)”을 각각 독립된 객체로 분리하고 상황에 맞게 선택하도록 설계하였다.
- 문자열을 어떤 규칙으로 분리할지는 Parser 인터페이스를 통해 동일한 메서드 시그니처로 추상화하고, 실제 구현은 각 파서 클래스가 담당한다.
- 기본 구분자인 쉼표(,)와 콜론(:)을 처리하는 CommaColonParser,
- 커스텀 구분자(//와 \n)를 처리하는 CustomParser 두 가지 구체적인 전략을 두어,
입력 형태에 따라 유연하게 객체를 선택할 수 있도록 했다.

- if-else문이 사라지고, 새로운 파싱 규칙이 추가되어도 기존 코드를 수정하지 않고 확장(OCP)할 수 있는 구조가 완성되었다.

- Parser의 각 구현체는 독립적인 책임을 가지므로, 테스트와 유지보수도 훨씬 용이해졌다.

**요약**
- 전략 패턴을 통해 CalculatorController는 “파싱이 어떻게 이루어지는지”에 대한 세부 구현을 몰라도 된다.
- 입력 문자열에 따라 적절한 resolver를 이용하여 파싱 전략(Parser)을 선택하기만 하면 되는 유연하고 확장 가능한 설계를 구현하고 실현하였다.

### TokenValidator interface

파서를 통해 파싱이된 문자열을 받아서 유효한지 판단하며 유효하지않으면 throw exception,
유효하다면 토큰화하는 인터페이스이다.

Parser는 전략패턴을 사용하였는데 TokenValidator에서는 왜 컴포지트패턴을 사용하였는지?

- Parser는 파싱 후 결과값을 리턴하는 방향이라 전략+어댑터 느낌이 강해서 전략선택에 포커스를 두었다.
- TokenValidator는 검사가 통과되면 그대로 리턴이고 아니면 throw exception이다보니, 결과값을 리턴하는 느낌보다도 검사기의 느낌이라고 생각하였다.
- 따라서 CompositeValidator를 두어 리프(null,number)들을 순회하며 검사하도록 하였다.
- 리졸버를 두는것도 리졸버에서 결정하도록하고 실행은 CompositeValidator가 하도록 하였다.
- Spring MVC에서도 view를 render하기전에 컨버터나 리졸버를 두듯이 선택 책임, 실행 책임을 분리해서 작성하는데 더 좋다라고 생각하였다.

**요약**
- Parser는 전략패턴으로 파싱방법을 선택하고 하나만 실행한다.
- TokenValidator는 컴포지트패턴으로 여러검증을 모두에게 적용한다.
- 이렇게하면 책임이 명확해지고, 확장성과 테스트용이성이 크게 올라간다.

## 5. 회고
단순한 문자열 계산기 문제였지만, if-else문이 굉장히 많아져서 빠르게 코드를 리팩토링하였다.
그러는 과정에서 단순한 문제가아닌 정말 많은 생각을 주게하는 문제였다. 각종 패턴들에 대한 고민, SOLID원칙을 최대한 지키자라는 생각과
이러한 웹어플리케이션을 만든다라면 어떤식으로 구조를 작성해야 유지보수성에 용이할까 생각하며 코드를 구현하였다.

아직은 기능이 많이 없는 계산기 이지만, 향후 추가될 기능들은 너무나도 많기때문에
**“변화에 유연한 구조를 만들자”** 라는 목표를 두고 설계하니 훨씬 많은 고민을 하게 되었다.  

전략패턴, 컴포지트패턴을 도입하였고 Parser를 전략패턴이 아닌 팩토리 패턴으로 구현하면 어떨까라는 생각을 하였다. 
만약 정적팩토리를 두게된다면 Mocking테스트가 어려워진다. 
Mocking테스트는 테스트런타임 환경에서 Parser를 테스트가 주도하여 교체할 수 있어야하는데 정적 팩토리는 Parser를 교체 할 수 없게된다.

Parser를 전략적으로 선택하여 파싱해야하는 성격이고 팩토리는 객체 선택 보다도 객체 생성에 포커스가 있다보니
팩토리패턴보다 전략패턴이 더 적합하다고 판단하였다.

물론, 리졸버를 통해 전략을 선택하고 Factory로 선택된 전략 인스턴스를 생성하는 방향도 정말 좋은 방법인것 같다.

여러가지 생각과 고민을 하면서 한층 더 성장하고 많이 공부해야겠다는 생각이 들었다.
유효성 검사, 파싱, 연산이 각각 독립된 책임을 가지도록 나누면서 OCP(개방-폐쇄 원칙)를 실질적으로 느낄 수 있었고,  
리팩토링 과정에서 객체지향 설계의 재미를 많이 배웠다.
“작동하는 코드”가 아니라 “유연하게 확장 가능한 코드”를 만들고 싶었다. 앞으로는 더더욱 이러한 객체지향적설계, SOLID원칙, 적합한 패턴 도입 등을 목표로 하여 
열심히 공부해보려고한다.
